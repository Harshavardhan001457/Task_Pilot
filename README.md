# ASTRA Sentinel V1 — Phase 2

Sentinel is a local-first secure action runtime. Phase 2 adds a deliberately small set of real, controlled OS capabilities behind the Phase 1 authorization and audit core.

## Architecture and lifecycle

`ActionRequest → validation → policy/permissions/risk → decision → capability → verification → audit → ActionResult`

The dispatcher is an OS-agnostic orchestrator. Capabilities are explicitly registered implementations of a small interface (`metadata`, `validate_parameters`, `execute`, `verify`); no caller can select Python objects or commands dynamically.

## Permissions and risk

Capabilities declare least-privilege permissions. The policy grants them per trusted requester (`cli`, `internal`). Risk levels are READ_ONLY (L0), LOW (L1), MODIFY (L2), DESTRUCTIVE (L3), and RESTRICTED (L4). Defaults allow L0/L1, disable L2, require trusted confirmation for L3, and deny L4. Explicit deny always wins over confirmation.

## Security principles

Unknown capabilities/requesters, malformed requests, missing permissions, and restricted actions fail closed. Untrusted request payloads permit exactly `capability`, `parameters`, and `requester`; IDs and timestamps are generated by Sentinel. There is no shell, dynamic import, `eval`, or `exec`. Audit records are structured and capabilities can declare fields to redact.

Phase 1 uses an in-memory audit implementation deliberately: it keeps tests deterministic and avoids retaining action metadata. Its `AuditLogger` interface allows a SQLite backend in a later phase.

## Configuration and manual requests

```python
from astra_sentinel import ActionRequest, build_default_runtime

dispatcher, audit = build_default_runtime()
request = ActionRequest.create(capability="application.open_app", parameters={"app": "vscode"}, requester="cli")
result = dispatcher.dispatch(request)
```

Set `ASTRA_WORKSPACE` to an existing directory before using filesystem capabilities. Missing or invalid configuration leaves the sandbox empty (fail closed); canonical paths are checked with `Path.relative_to`, not string prefixes. To register VS Code, set `ASTRA_VSCODE_EXECUTABLE` to an existing absolute `Code.exe` path. Callers supply `vscode`, never an executable or command.

Available capabilities are `application.open_app`, `application.is_app_running`, `filesystem.find_file`, `filesystem.get_file_info`, `filesystem.open_file`, and `filesystem.create_dir`. Creating a directory additionally requires trusted configuration to grant `filesystem.write` and enable L2/MODIFY.

Manual equivalents: `open app vscode`, `is app running vscode`, `find file dbms.pdf`, `get file info dbms.pdf`, `open file dbms.pdf`, and `create dir ASTRA_Test` are all ActionRequests using the corresponding names above.

## Current limitations

There is no authentication, persistent audit log, or confirmation UI. Native associated-file opening and process checking currently support Windows; unsupported platforms fail safely. No delete, rename, move, process-kill, shell command, remote, GUI, or plugin capability exists.
