# ASTRA Sentinel V1 — Phase 1

Sentinel is a local-first secure action runtime. Phase 1 builds the authorization and audit core without any real operating-system actions.

## Architecture and lifecycle

`ActionRequest → validation → policy/permissions/risk → decision → mock capability → verification → audit → ActionResult`

The dispatcher is an OS-agnostic orchestrator. Capabilities are explicitly registered implementations of a small interface (`metadata`, `validate_parameters`, `execute`, `verify`); no caller can select Python objects or commands dynamically.

## Permissions and risk

Capabilities declare least-privilege permissions. The policy grants them per trusted requester (`cli`, `internal`). Risk levels are READ_ONLY (L0), LOW (L1), MODIFY (L2), DESTRUCTIVE (L3), and RESTRICTED (L4). Defaults allow L0/L1 mock actions, disable L2, require trusted confirmation for L3, and deny L4. Explicit deny always wins over confirmation.

## Security principles

Unknown capabilities/requesters, malformed requests, missing permissions, and restricted actions fail closed. Untrusted request payloads permit exactly `capability`, `parameters`, and `requester`; IDs and timestamps are generated by Sentinel. There is no shell, subprocess, dynamic import, `eval`, `exec`, or real OS capability. Audit records are structured and capabilities can declare fields to redact.

Phase 1 uses an in-memory audit implementation deliberately: it keeps tests deterministic and avoids retaining action metadata. Its `AuditLogger` interface allows a SQLite backend in a later phase.

## Example mock request

```python
from astra_sentinel import ActionRequest, build_default_runtime

dispatcher, audit = build_default_runtime()
request = ActionRequest.create(
    capability="mock.echo", parameters={"message": "hello"}, requester="cli"
)
result = dispatcher.dispatch(request)
```

## Current limitations and Phase 2

There is no authentication, persistent audit log, confirmation UI, or OS action. Phase 2 can add explicit platform-specific capabilities behind the existing capability interface, plus trusted confirmation and a persistence backend, without changing the core pipeline.
